Irrelevante con 1 TB en 50 máquinas. Con 2 GB en un portátil, domina.

La misma consulta: Pandas y Polars

# Pandas: cada paso corre al momento
o = pd.read_parquet(ORDERS, columns=["customer_id", "product_id",
                                     "quantity", "price", "order_date"])
o = o[o["order_date"] >= CUTOFF]
o = o.assign(revenue=o["price"] * o["quantity"])
df = o.merge(c, on="customer_id").merge(p, on="product_id")
df.groupby(["segment", "category"], as_index=False) \
  .agg(orders=("revenue", "size"), revenue=("revenue", "sum"))

# Polars: arma un plan, corre en collect()
(pl.scan_parquet(ORDERS)
   .filter(pl.col("order_date") >= pl.date(2024, 7, 1))
   .with_columns(revenue=pl.col("price") * pl.col("quantity"))
   .join(c, on="customer_id").join(p, on="product_id")
   .group_by("segment", "category")
   .agg(orders=pl.len(), revenue=pl.col("revenue").sum())
   .collect())

La misma consulta: DuckDB y Spark

# DuckDB: SQL puro sobre los archivos, sin paso de lectura
duckdb.sql(f"""
    SELECT c.segment, p.category, COUNT(*) AS orders,
           SUM(o.price * o.quantity) AS revenue
    FROM '{ORDERS}' o
    JOIN '{CUSTOMERS}' c USING (customer_id)
    JOIN '{PRODUCTS}'  p USING (product_id)
    WHERE o.order_date >= DATE '{CUTOFF}'
    GROUP BY ALL
""").df()

# Spark
(spark.read.parquet(ORDERS)
   .filter(F.col("order_date") >= CUTOFF)
   .withColumn("revenue", F.col("price") * F.col("quantity"))
   .join(c, "customer_id").join(p, "product_id")
   .groupBy("segment", "category")
   .agg(F.count("*").alias("orders"), F.sum("revenue").alias("revenue")))

Cómo leer los resultados

Los números varían con la máquina, pero el orden suele repetirse:

  • Polars y DuckDB suelen ser los más rápidos
  • Pandas hace los joins en un núcleo y materializa cada paso
  • Spark paga su costo fijo: planificación, tasks, transferencia a Python
  • Pandas API on Spark suma la traducción de la semántica de Pandas: hecha para escalar, no para ser rápida en una máquina

Memoria: Pandas suele romperse por falta de RAM mucho antes de ser demasiado lento. Regla antigua: reserva de 5 a 10 veces el tamaño de los datos.

Cuando crece el volumen

La misma consulta con 1, 5 y 20 millones de filas:

  • El costo fijo de Spark pesa más con poco volumen; la diferencia relativa baja al crecer
  • Pandas crece más rápido que los demás y en algún punto deja de caber en memoria
  • Polars y DuckDB crecen despacio: todos los núcleos, sin materializar pasos intermedios

La curva que un notebook no puede mostrar: Spark en un clúster. Con 10 máquinas, el mismo código procesa 10 veces más datos en el mismo tiempo.

Pandas API on Spark

Caso de uso: migración. Código Pandas que funciona y cuyos datos ya no caben en una máquina.

import pyspark.pandas as ps          # en vez de: import pandas as pd
df = ps.read_parquet(path)
df.groupby("x")["y"].mean()          # mismo código

El índice por defecto

compute.default_index_type:

Tipo Cómo se genera Costo
sequence (por defecto) 0, 1, 2… en una sola partición Cuello de botella: una task ve todos los datos
distributed-sequence 0, 1, 2… calculado por partición Medio: un job extra
distributed IDs crecientes, no consecutivos Bajo: úsalo si el índice no importa

Polars: eager o lazy

pl.read_parquet ejecuta cada paso al momento. pl.scan_parquet arma un plan que corre en .collect().

PySpark Polars
F.col("x") pl.col("x")
df.withColumn("y", expr) df.with_columns(y=expr)
df.groupBy("k").agg(...) df.group_by("k").agg(...)
F.when(c, a).otherwise(b) pl.when(c).then(a).otherwise(b)
F.sum("x").over(Window.partitionBy("k")) pl.col("x").sum().over("k")

lazy.explain() muestra predicate y column pruning. collect(engine="streaming") procesa datos mayores que la memoria.

DuckDB: analítica dentro de tu proceso

Sin servidor, como SQLite, pero optimizado para consultas analíticas.

# 1) SQL sobre archivos (Parquet, CSV, JSON, comodines, S3)
duckdb.sql(f"SELECT region, AVG(price) FROM '{ORDERS}' GROUP BY region")

# 2) SQL sobre un DataFrame en memoria: la variable se vuelve tabla
regions_pd = pd.DataFrame({"region": REGIONS, "manager": managers})
duckdb.sql(f"SELECT * FROM '{ORDERS}' JOIN regions_pd USING (region)").pl()

# 3) Out-of-core: usa disco en vez de romperse
con = duckdb.connect()
con.sql("SET memory_limit = '300MB'")
con.sql(f"SET temp_directory = '{BASE}/duckdb_tmp'")

En PySpark 4.0, Arrow viene apagado por defecto para toPandas() y createDataFrame(pandas_df). Enciéndelo:

.config("spark.sql.execution.arrow.pyspark.enabled", "true")

Cómo decidir

Situación Herramienta
Decenas de GB a TB, o datos que crecerán mucho Spark
Streaming, Delta Lake, MLlib, ya hay un clúster Spark
Código Pandas que ya no cabe en memoria Pandas API on Spark
Hasta decenas de GB en una máquina, equipo de SQL DuckDB
Hasta decenas de GB en una máquina, pipeline en Python Polars
Exploración rápida, pocos MB Pandas

Spark no es solo velocidad: trae tolerancia a fallos, escala horizontal y un ecosistema.
