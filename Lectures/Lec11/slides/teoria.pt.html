Irrelevante com 1 TB em 50 máquinas. Com 2 GB em um notebook, domina.

A mesma consulta: Pandas e Polars

# Pandas: cada passo roda na hora
o = pd.read_parquet(ORDERS, columns=["customer_id", "product_id",
                                     "quantity", "price", "order_date"])
o = o[o["order_date"] >= CUTOFF]
o = o.assign(revenue=o["price"] * o["quantity"])
df = o.merge(c, on="customer_id").merge(p, on="product_id")
df.groupby(["segment", "category"], as_index=False) \
  .agg(orders=("revenue", "size"), revenue=("revenue", "sum"))

# Polars: monta um plano, roda no collect()
(pl.scan_parquet(ORDERS)
   .filter(pl.col("order_date") >= pl.date(2024, 7, 1))
   .with_columns(revenue=pl.col("price") * pl.col("quantity"))
   .join(c, on="customer_id").join(p, on="product_id")
   .group_by("segment", "category")
   .agg(orders=pl.len(), revenue=pl.col("revenue").sum())
   .collect())

A mesma consulta: DuckDB e Spark

# DuckDB: SQL puro sobre os arquivos, sem passo de leitura
duckdb.sql(f"""
    SELECT c.segment, p.category, COUNT(*) AS orders,
           SUM(o.price * o.quantity) AS revenue
    FROM '{ORDERS}' o
    JOIN '{CUSTOMERS}' c USING (customer_id)
    JOIN '{PRODUCTS}'  p USING (product_id)
    WHERE o.order_date >= DATE '{CUTOFF}'
    GROUP BY ALL
""").df()

# Spark
(spark.read.parquet(ORDERS)
   .filter(F.col("order_date") >= CUTOFF)
   .withColumn("revenue", F.col("price") * F.col("quantity"))
   .join(c, "customer_id").join(p, "product_id")
   .groupBy("segment", "category")
   .agg(F.count("*").alias("orders"), F.sum("revenue").alias("revenue")))

Como ler os resultados

Os números variam com a máquina, mas a ordem costuma se repetir:

  • Polars e DuckDB costumam ser os mais rápidos
  • Pandas faz os joins em um núcleo e materializa cada passo
  • Spark paga seu custo fixo: planejamento, tasks, transferência para Python
  • Pandas API on Spark soma a tradução da semântica do Pandas: feita para escalar, não para ser rápida em uma máquina

Memória: o Pandas costuma quebrar por falta de RAM bem antes de ficar lento demais. Regra antiga: reserve de 5 a 10 vezes o tamanho dos dados.

Quando o volume cresce

A mesma consulta com 1, 5 e 20 milhões de linhas:

  • O custo fixo do Spark pesa mais com pouco volume; a diferença relativa cai ao crescer
  • O Pandas cresce mais rápido que os outros e em algum ponto deixa de caber na memória
  • Polars e DuckDB crescem devagar: todos os núcleos, sem materializar passos intermediários

A curva que um notebook não consegue mostrar: Spark em um cluster. Com 10 máquinas, o mesmo código processa 10 vezes mais dados no mesmo tempo.

Pandas API on Spark

Caso de uso: migração. Código Pandas que funciona e cujos dados não cabem mais em uma máquina.

import pyspark.pandas as ps          # em vez de: import pandas as pd
df = ps.read_parquet(path)
df.groupby("x")["y"].mean()          # mesmo código
Tema Pandas Pandas API on Spark
Índice Sempre existe Precisa ser gerado; o tipo afeta a performance
Ordem das linhas Garantida Não garantida após operações distribuídas
iterrows, .to_numpy() Normais Trazem tudo para o driver
Modo ANSI do Spark 4 — Precisa estar desligado

O índice padrão

Tipo Como gera Custo

distributed-sequence 0, 1, 2… calculado por partição Médio: um job extra
distributed IDs crescentes, não consecutivos Baixo: use quando o índice não importa

Polars: eager ou lazy

pl.read_parquet executa cada passo na hora. pl.scan_parquet monta um plano que roda no .collect().

PySpark Polars
F.col("x") pl.col("x")
df.withColumn("y", expr) df.with_columns(y=expr)
df.groupBy("k").agg(...) df.group_by("k").agg(...)
F.when(c, a).otherwise(b) pl.when(c).then(a).otherwise(b)
F.sum("x").over(Window.partitionBy("k")) pl.col("x").sum().over("k")

lazy.explain() mostra predicate e column pruning. collect(engine="streaming") processa dados maiores que a memória.

DuckDB: analítica dentro do seu processo

Sem servidor, como o SQLite, mas otimizado para consultas analíticas.

# 1) SQL sobre arquivos (Parquet, CSV, JSON, curingas, S3)
duckdb.sql(f"SELECT region, AVG(price) FROM '{ORDERS}' GROUP BY region")

# 2) SQL sobre um DataFrame na memória: a variável vira tabela
regions_pd = pd.DataFrame({"region": REGIONS, "manager": managers})
duckdb.sql(f"SELECT * FROM '{ORDERS}' JOIN regions_pd USING (region)").pl()

# 3) Out-of-core: usa disco em vez de quebrar
con = duckdb.connect()
con.sql("SET memory_limit = '300MB'")
con.sql(f"SET temp_directory = '{BASE}/duckdb_tmp'")

Apache Arrow: a língua comum

                  ┌───────────────┐
  Pandas ◀──────▶ │               │ ◀──────▶ Polars
                  │ Apache Arrow  │
  DuckDB ◀──────▶ │ (colunar, na  │ ◀──────▶ Spark
                  │  memória)     │
 Parquet ◀──────▶ │               │ ◀──────▶ ML
                  └───────────────┘

No PySpark 4.0, o Arrow vem desligado por padrão em toPandas() e createDataFrame(pandas_df). Ligue-o:

.config("spark.sql.execution.arrow.pyspark.enabled", "true")
