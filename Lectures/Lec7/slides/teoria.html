1. Design assumptions

A system is explained by its assumptions

Hadoop implements two Google papers: GFS (2003) and MapReduce (2004). GFS opens by stating what it assumes, and each decision follows from that:

Assumption (GFS, §2.1) Decision Consequence you still see today
Components fail all the time Replication, automatic recovery Tasks are retried
Files are huge Large blocks The small files problem
Reads are large and sequential No caching of data on the client Bad at random access
Writes append, and do not modify Write-once No UPDATE: hence Delta and Iceberg
Throughput matters more than latency Batch design Tens of seconds per job

The method for this lecture: take each mechanism and ask which assumption justifies it. On changing the assumptions, as the cloud did by separating storage and computing, the design has to change too. That is why part of Hadoop has aged, and part has not.

2. HDFS: the numbers behind the design

Architecture: separating metadata from data

              1. where are the blocks of sales.csv?
   Client ─────────────────────────────────────────▶ NameNode
     │   ◀───────── A: nodes 1, 2, 4 ──────────────  namespace + block map, IN MEMORY
     │ 2. read directly                                  ▲ heartbeats, block reports
     ▼                                                   │
   DataNode 1 [A][C]   DataNode 2 [A][B]   DataNode 3 [B][C]   DataNode 4 [A][C]

The key decision: data never passes through the NameNode. So a single process can coordinate thousands of nodes, since its load depends on the number of metadata operations, and not on the bytes read.

Mechanism Purpose
EditLog + FsImage Durable metadata: the map in memory is rebuilt from disk
Heartbeat No signal for over 10 min: the node is dead, and its blocks are re-replicated
Checksums Clients verify on read; on a mismatch, they use another replica

The price: the NameNode’s memory limits the number of files, and its failure stops the whole file system unless high availability is configured.

Why 128 MB? Two independent reasons

1. Disk. Reading a block costs a seek, then a transfer. To keep seeks below 1% of the time, with seek time \(t_s\) and rate \(r\):

\[\frac{t_s}{B / r} \leq 0.01 \quad\Longrightarrow\quad B \geq 100\, t_s\, r\]

With \(t_s = 10\) ms and \(r = 200\) MB/s: \(B \geq\) 200 MB. The same order as the 128 MB default (64 MB in the original GFS, with slower disks).

2. Metadata. Each file and block takes up about 150 bytes of NameNode heap (rule of thumb, not a constant). For 1 PB, counting one file and one block per object:

File size Files Objects NameNode heap
128 MB 7.8 million 15.6 million 2.3 GB
1 MB 1 billion 2 billion 300 GB

Same data, 128× the memory: this is the small files problem, and it also slows reads, since each file costs a round trip to the NameNode. It is the reason to compact files (coalesce before writing, OPTIMIZE in Delta).

How likely is it to lose data?

Replicas on 3 random nodes out of \(N\). If \(k\) nodes fail at the same time, a given block is lost if its 3 replicas are among them:

\[P(\text{block lost}) = \binom{k}{3} \Big/ \binom{N}{3}\]

With \(N = 1000\) nodes and \(B = 10^7\) blocks, the expected loss is \(B \cdot P\):

Simultaneous failures \(P\) per block Blocks lost (expected)
\(k = 2\) 0 0
\(k = 3\) \(6 \times 10^{-9}\) 0.06
\(k = 10\) (1%, e.g. power loss) \(7.2 \times 10^{-7}\) 7.2

Two lessons:

  • Independent failures are almost harmless, since re-replication closes the window quickly. Correlated failures are what lose data (Cidon et al., 2013).
  • With many blocks, some block almost always has all its replicas among the failed nodes, however unlikely it is for any one block.

Placement and its alternatives

Rack-aware placement targets the correlated case (HDFS design): one replica on the writer’s node, and two on another rack.

Replication Survives Storage Writes Reads
3 replicas, random 2 nodes 3× Pipeline to 3 Any of 3
3 replicas, 2 racks 2 nodes or 1 rack 3× Less inter-rack traffic Any of 3
Erasure code RS(6,3) Any 3 of 9 pieces 1.5× CPU to encode Must rebuild if a piece is lost

Erasure coding splits 6 data pieces and adds 3 parity pieces. It tolerates more failures than replication with half the storage. So why is replication still used?

  • Locality: a replicated block can be read whole on 3 nodes; a coded one is spread out.
  • Recovery: rebuilding a lost piece reads 6 others across the network.

Rule of use: replicas for hot data, erasure coding for cold data. Cloud object stores make the same trade-off internally.

Data locality: a probability, not a guarantee

“Move the code to the data” needs a free slot on a node holding the block. If a fraction \(u\) of the slots is busy, and the \(r\) replica nodes are independent:

\[P(\text{a local slot is free}) = 1 - u^{\,r}\]

Cluster load \(u\) \(r = 1\) \(r = 3\)
50% 50% 88%
90% 10% 27%

So replication also buys locality, not only safety, and locality falls just when the cluster is busiest.

Spark’s answer is delay scheduling (Zaharia et al., 2010): when no local slot is free, wait a short time for one before giving up, from process-local to node-local, rack-local and any. In Spark, spark.locality.wait defaults to 3 s.

A trade-off without a universal value: a long wait keeps tasks local but holds idle slots. And in a cloud setup with S3, there is no locality to preserve: the level is always ANY.

3. MapReduce: model, failures, limits

The model, in two signatures

Dean and Ghemawat (2004) define the entire programming model with:

\[\text{map}\ (k_1, v_1) \to \text{list}(k_2, v_2) \qquad\quad \text{reduce}\ (k_2, \text{list}(v_2)) \to \text{list}(v_2)\]

The framework does everything else: partition, schedule, group by \(k_2\) and retry.

 split 1 ─▶ map ─┐ partition    ┌─ sort, merge ─▶ reduce ─▶ out 1
 split 2 ─▶ map ─┼─ hash(k2)%R ─┤
 split 3 ─▶ map ─┘ local disk   └─ sort, merge ─▶ reduce ─▶ out 2
   M map tasks                     R reduce tasks        on GFS/HDFS

Why such a narrow model? Because restricting the program is what lets the system parallelize and recover automatically. If map and reduce are deterministic functions of their input, re-running them gives the same output: re-execution is fault tolerance, and the distributed result equals a sequential one (§3.3).

This is the same idea as Spark’s lineage, and the same reason a UDF should be deterministic.

Failures and stragglers

Event What happens Why
A map worker dies, task finished Re-executed Its output was on that machine’s local disk
A reduce worker dies, task finished Not re-executed Its output is already in GFS, replicated
Any task in progress Re-executed elsewhere Nothing committed yet
The master dies The job fails (in the paper) Assumed to be rare: only one machine

Stragglers. A machine may be far slower than the others, due to a bad disk or a busy node, and by the time bound \(T \geq t_{\max}\), that task sets the job’s end.

Backup tasks: when the job is nearly done, the framework launches copies of the remaining tasks, and whichever finishes first wins. The paper’s sort takes 44% longer without them (§3.6).

This is safe only because tasks are deterministic. Spark’s version is spark.speculation, off by default.

State at the master: \(O(M + R)\) scheduling decisions and \(O(M \cdot R)\) state: the same \(M \times R\) as in the shuffle’s block count.

Why MapReduce lost: the cost of a chain

Each job reads from and writes to HDFS with replication. For \(j\) steps on data of size \(D\), with \(r = 3\):

\[\text{bytes written} = j \cdot r \cdot D \qquad\quad \text{bytes over the network} \geq j \cdot (r - 1) \cdot D\]

Example: \(D\) = 100 GB, \(j = 10\) iterations of an ML algorithm: 3 TB written, 2 TB of it through the network, just for persisting intermediate results that nobody will reuse.

MapReduce Spark
Intermediate results HDFS: durable, 3× Memory or local disk, 1×
A failure Restart from the last HDFS write Recompute from lineage
Plan Each job in isolation The whole DAG, optimized

The trade-off is real, and Spark did not eliminate it. MapReduce pays a fixed cost for durability at each step. Spark bets on failures being rare enough for recomputation to come out cheaper than always writing. On very long jobs with frequent failures, this bet may lose, and that is what checkpoint is for.

4. YARN: allocating a cluster

Two levels of decision

Hadoop 1 mixed resource management and job scheduling in a single process. YARN separates them: the ResourceManager allocates containers to applications, and each ApplicationMaster decides how to use its own. This is what allows Spark, Flink and MapReduce to share a cluster.

YARN In Spark Sizing question
Container Executor Cores and memory of each
ApplicationMaster Driver in cluster mode Where the driver runs
Queue --queue What fraction each team may use

Exercise. 20 nodes, each with 16 cores and 64 GB. With --executor-cores 4 --executor-memory 8g, how many executors fit, and which resource limits them? Memory overhead: max(10%, 384 MiB).

Container: \(8 + 0.8 =\) 8.8 GB. Per node: cores \(16/4 =\) 4; memory \(64/8.8 =\) 7. Cores are the limit: 4 executors per node, 35 GB used, and 29 GB wasted.

Total \(20 \times 4 = 80\) executors, 320 task slots. With 14 GB each, it would be balanced: \(15.4 \times 4 \approx\) 62 GB.

Why not one huge executor? Very large heaps lengthen GC pauses, and each executor is a failure unit: losing one loses more cached data and more shuffle output.

5. FileSystem API and object stores

One interface, different guarantees

Spark never talks directly to a disk. It calls Hadoop’s FileSystem interface, and the URL scheme picks the implementation: file://, hdfs://, s3a://, gs://, abfs://.

The interface is the same, but the semantics are not. An object store is a key-value map that merely looks like a tree:

Operation HDFS S3 and similar
rename(dir) Atomic, \(O(1)\): changes metadata Copy + delete, \(O(\text{bytes})\), not atomic
list(dir) One NameNode call Paged requests by prefix
Locality Yes No: all reads go through the network
Append Yes No
Cost model Machines Per request and per GB

Why this matters: Hadoop’s classic output commit writes to a temporary folder, then renames it to publish atomically. On S3, that rename is slow, and a crash midway leaves a partial result. This is why S3A committers exist, and it is the main motivation for table formats like Delta, where a commit is one atomic log write (Lecture 9).

6. Integrating problem

Sizing an HDFS cluster

500 TB of data, \(r = 3\), nodes with 48 TB of disk (12 disks at 200 MB/s). Average file: 1 GB.

  1. How many nodes for storage? 2. How much NameNode heap? 3. How much if the files were 1 MB? 4. How long does a full scan take? 5. How much would RS(6,3) save?
  1. Raw: \(500 \times 3 =\) 1,500 TB, so \(1500 / 48 =\) 32 nodes, with no spare room. Keeping 25% free: 40 nodes.
  2. \(500{,}000\) files + \(500\ \text{TB} / 128\ \text{MB} \approx 3.9\) M blocks \(=\) 4.4 M objects \(\times\) 150 B \(\approx\) 660 MB.
  3. 500 M files + 500 M blocks \(=\) \(10^9 \times 150\) B \(=\) 150 GB: same data, 227× the heap.
  4. 32 nodes \(\times\) 12 \(\times\) 200 MB/s \(=\) 76.8 GB/s; \(500\ \text{TB} / 76.8\ \text{GB/s} \approx\) 1.8 h. CPU and network come on top.
  5. \(500 \times 1.5 =\) 750 TB: half the disks. In exchange: less locality, and costlier recovery. So use it for cold data.

The heap in (2) is trivial, and (3) is a serious problem. The data’s volume did not change: its organization did.
