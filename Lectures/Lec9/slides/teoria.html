1. What plain Parquet cannot do

A table as “a folder of files”

The folder’s contents define the table. On an object store, with no atomic multi-file operations, that causes specific anomalies:

Anomaly Scenario ACID property violated
Partial write A job dies with 60 of its 100 files written Atomicity
Dirty read A reader lists the folder during an overwrite: old and new files together Isolation
Lost update Two jobs rewrite one partition: the last one erases the other’s work Isolation
Invalid data A file with other columns lands in the folder Consistency

And there are performance problems, even with no failures: to plan a query, listing the folder on S3 takes one request per 1,000 objects (Armbrust et al., 2020), and each file’s footer needs its own request.

The insight of Delta Lake: do not change the storage. Add one level of indirection: the table is not “what is in the folder”, it is “what a log says is in the folder”.

2. The transaction log

The table is the replay of its log

Each commit \(v\) is a JSON file listing the files it adds (\(A_v\)) and removes (\(R_v\)). The table’s state is a pure function of the log:

\[S_v = (S_{v-1} \setminus R_v) \cup A_v\]

 _delta_log/
   00000000000000000000.json    add a, add b, add c, metaData(schema)
   00000000000000000001.json    add d
   00000000000000000002.json    remove b, add e         (an UPDATE)
   00000000000000000003.json    remove a, remove c, add f   (OPTIMIZE, dataChange=false)
 a.parquet  b.parquet  c.parquet  d.parquet  e.parquet  f.parquet

Exercise: which files make up version 2? And version 3?

  • \(S_0 = \{a, b, c\}\), \(S_1 = \{a, b, c, d\}\), \(S_2 =\) \(\{a, c, d, e\}\), \(S_3 =\) \(\{d, e, f\}\).
  • b.parquet still exists on disk, but no longer belongs to the table: a reader of version 3 never opens it.
  • Why this yields atomicity: a job first writes all its data files, invisible because no log entry refers to them, then commits with a single file. A crash before that commit simply leaves orphan files.
  • Time travel needs nothing else: replaying up to \(v\) gives the table at version \(v\).

The one primitive it needs: put-if-absent

Write protocol (Armbrust et al., 2020, §3.2.2):

  1. Find the latest version \(r\), and read the table at \(r\) if needed.
  2. Write the new data files, with unique names, in parallel.
  3. Try to create the log file \(r + 1\), only if it does not exist.
  4. If another writer got there first: check for conflicts, and retry at the next version.

Step 3 is the only point of coordination. The whole transaction reduces to one atomic operation on one small object: create this key if absent.

Storage How put-if-absent is obtained
HDFS, Azure Atomic rename, or native conditional operations
S3 Did not exist in the paper: needed coordination. Conditional writes arrived in 2024
Google Cloud Storage Native conditional writes

This explains the system’s limit: one commit per object store write. With tens to hundreds of milliseconds per write, the paper reports several transactions per second. It is fine for batch and micro-batch, and makes it the wrong tool for per-row OLTP.

ACID, property by property

Property How it is obtained What it does not give
Atomicity One log file per commit: all or nothing Across several tables there is no atomicity
Consistency Schema enforcement, and constraints on write Your business rules are your own
Isolation Readers read a fixed version; writers validate on commit No multi-statement transactions
Durability The object store’s durability Depends on the storage and on VACUUM

Checkpoints: keeping reads fast. Replaying thousands of JSON files would be slow. So by default every 10 commits, the state is written to a Parquet checkpoint, and a reader needs only:

\[\text{latest checkpoint} + \text{the JSON files after it}\]

The checkpoint is itself an analytical table about the table: since it stores per-file statistics in columnar form, finding which files to read is usually faster than LIST plus reading footers (Armbrust et al., 2020, §3.1.3).

A checkpoint only affects performance: a crash while writing one cannot corrupt anything.

3. Concurrency control

Optimistic: assume no conflict, then verify

Approach Idea Fits when
Pessimistic (locks) Ask permission before working Short transactions, frequent conflicts
Optimistic Work first, and validate at commit Long transactions, rare conflicts

A Spark job may last hours and touch thousands of files, so holding locks for that long is out of the question. Besides, an object store offers no lock service.

Readers never block anyone. They read the snapshot at \(v\), whose files stay immutable, so any number of them may run during a write.

The price of optimism is wasted work: on a conflict, the job’s writes are discarded and it must retry. With a commit probability of conflict \(p\) on each attempt, the expected number of attempts is:

\[E[\text{attempts}] = \frac{1}{1 - p}\]

With \(p = 50\%\): 2 attempts, so twice the cost, on a job that may take an hour. Design so that writers do not touch the same data, rather than rely on retries.

What conflicts with what, and why

The Delta documentation’s matrix:

INSERT UPDATE, DELETE, MERGE Compaction
INSERT Cannot conflict Can Cannot
UPDATE, DELETE, MERGE Can Can
Compaction Can

It all follows from one question: did the other commit change what I read?

Exercise: why do these results make sense?

  • Two blind INSERTs: neither read anything, and new files have unique names. So both orders give the same result.
  • INSERT vs MERGE: the MERGE searched the table for matches, and the new rows may be matches it did not see (ConcurrentAppendException).
  • Two MERGEs on the same files: both remove a file the other used (ConcurrentDeleteReadException).
  • MERGE vs compaction: compaction marks files as removed, even if the data is unchanged.

The common fix: make the conditions disjoint, with an explicit partition predicate, MERGE ... ON t.id = s.id AND t.date = '2024-07-04', so that the operation reads only that partition.

4. The cost of UPDATE and MERGE

Parquet is immutable, so changing a row rewrites a file

UPDATE does not update anything: it finds the affected files, rewrites each one whole, and commits remove old + add new. This is copy-on-write.

How many files does a MERGE touch? With \(k\) updates spread randomly over \(F\) files, the expected number of touched files is (balls and bins):

\[F\left(1 - \left(1 - \frac{1}{F}\right)^{k}\right) \approx F\left(1 - e^{-k/F}\right)\]

Updated rows \(k\) Files \(F\) Files rewritten Fraction of the table
100 1,000 95 10%
1,000 1,000 632 63%
5,000 1,000 993 99%

1,000 rows can force rewriting 63% of a table. If the table holds 1 TB, that is 630 GB written for perhaps a few KB of real changes.

What saves you is correlation. If updates concentrate in recent data, and the table is partitioned or sorted by date, they touch only a few files. The formula assumes random placement: the data’s layout is what you can change.

MERGE step by step, and its alternative

 1. Join source and target, to find which files contain matches     (reads: all candidates)
 2. Rewrite each file with a match: updated rows + unchanged rows   (writes: whole files)
 3. Commit: remove the old files, add the new ones                  (one atomic log entry)
To lower the cost Why
Partition predicate in ON Reduces the candidates in step 1
Deduplicate the source Two source rows for one target row make the MERGE fail: which would win?
Copy-on-write Merge-on-read (deletion vectors)
Update Rewrites the file Marks the rows as deleted in a side file
Write cost High Low
Read cost None Must filter marked rows, until compaction

The cost does not vanish: it moves from write to read.

5. Reading less: skipping and Z-order

Data skipping needs clustered data

The log stores min, max and null counts per file, by default for the first 32 columns. A filter skips any file whose range cannot match. So skipping works only if each file has a narrow range, that is, if related rows are together.

A sort helps only one column. How can several be served at once? Z-order interleaves the bits of the columns:

\[x = \color{#7cc}{1}\color{#7cc}{0},\ \ y = \color{#fc8}{1}\color{#fc8}{1} \quad\Longrightarrow\quad z = \color{#7cc}{1}\color{#fc8}{1}\color{#7cc}{0}\color{#fc8}{1}\]

Sorting by \(z\) places nearby points together in all the dimensions, approximately. With \(F\) files and \(d\) columns, a filter on one column touches about \(F^{\,1 - 1/d}\) files:

Columns in Z-order Files touched (\(F = 10{,}000\)) Fraction read
1 (plain sort) 1 0.01%, on that column only
2 100 1%
3 464 4.6%
4 1,000 10%

The docs warn that “the effectiveness of the locality drops with each extra column”. The paper measures this with 4 columns: it could skip at least 43% of files per dimension, and 54% on average.

6. Versions, retention and deletion

When is data really gone?

DELETE only writes a remove to the log: the data stays on disk, and time travel can read it. Two retention periods decide what happens next:

Setting Default Controls Enforced by
delta.deletedFileRetentionDuration 1 week How long removed data files are kept Manual VACUUM
delta.logRetentionDuration 30 days How long log entries are kept Automatic, after checkpoints

Time travel to version \(v\) needs both its log entries and its data files, so the effective window is the shorter of the two.

Scenario Consequence
VACUUM is never run Storage grows forever, and “deleted” personal data stays readable
VACUUM with a short retention Concurrent readers on an old version lose their files: hence the safety check
Legal request to erase a customer’s data DELETE is not enough: it needs VACUUM after retention

RESTORE writes a new commit: it does not rewind history, so it can itself be undone.

7. Integrating problem

A MERGE that grew too expensive

Silver: 2 TB in 2,000 files, with 1 GB each. Every day: a MERGE of 20,000 updates and new rows, and a nightly OPTIMIZE. Lately MERGE takes 3 hours and sometimes fails with ConcurrentDeleteReadException.

  1. How much does MERGE rewrite, with updates spread randomly? 2. What explains the exception? 3. 95% of the updates fall within the last 7 days: what would you change? 4. How much would it rewrite then?
  1. \(k/F = 10\), so \(F(1 - e^{-10}) \approx\) 2,000 files: the whole table, 2 TB rewritten each day.
  2. OPTIMIZE removes files that the long MERGE has read. They overlap in time, and the matrix says compaction can conflict.
  3. Partition by date, and add t.order_date >= current_date() - 7 to the ON clause (with a separate pass for old updates). Also schedule OPTIMIZE so as not to overlap, or limit it to old partitions.
  4. A year in 2,000 files is about 5.5 files per day, so 7 days has about 38 files, or 38 GB: about 50× less. \(k\) remains large, so all those files get touched, but \(F\) has shrunk.

The lesson: no configuration fixes this as much as the data’s layout.
