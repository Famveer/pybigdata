The unbounded table

The stream is a table that never stops growing. You write the query as if over the whole table; Spark runs it incrementally.

   source     [e1 e2]        [e3 e4 e5]        [e6]
                 │               │               │
   query      groupBy        groupBy        groupBy
                 │               │               │
   result     [A:2]          [A:3 B:2]      [A:3 B:3]
   SOURCE ──▶ TRANSFORMATIONS ──▶ SINK
              CHECKPOINT: processed offsets + aggregation state
              TRIGGER   : when each micro-batch runs

Output modes

Mode Written in each micro-batch Typical use
append Only new rows that will not change Events without aggregation; windows closed by the watermark
update Only result rows that changed Dashboards, upserts
complete The entire result, again Small aggregations

Processing time: when Spark received the event. Event time: when it happened. For business metrics, we almost always want event time, which requires handling late data.

File sources: two precautions

  • The schema is mandatory: it must stay stable for the life of the query
  • Files must appear complete: write elsewhere, then move (atomic on the same file system)
orders_stream = (spark.readStream.schema(event_schema)
                 .option("maxFilesPerTrigger", 1).json(INPUT))

q = (orders_stream.groupBy("region").count()
     .writeStream.format("memory").queryName("by_region")
     .outputMode("complete").start())

Windows

.groupBy(F.window("event_time", "5 minutes"))                # tumbling
.groupBy(F.window("event_time", "10 minutes", "5 minutes"))  # sliding
  Tumbling (5 min)                         Sliding (10 min, every 5 min)
  |10:00-10:05|10:05-10:10|10:10-10:15|    |10:00-------10:10|
                                                 |10:05-------10:15|
  each event falls in 1 window             each event falls in 2 windows

Watermark

  watermark = latest event_time seen − tolerated delay

  tolerated delay 5 min, latest event_time = 10:11  ->  watermark = 10:06

  - window 10:00-10:05 -> end < watermark: closed, emitted, state released
  - event at 10:07     -> window 10:05-10:10 still open: accepted
  - event at 10:02     -> its window is closed: dropped

Trade-off: a larger delay accepts more late events, but holds more state in memory and delays results.

Checkpoint

  checkpoint/
  ├── offsets/    <- what each micro-batch will read (written BEFORE processing)
  ├── commits/    <- which micro-batches finished    (written AFTER the sink)
  ├── sources/    <- files already seen by the source
  └── state/      <- aggregation and window state

Restarting with the same checkpoint resumes where it stopped. With a transactional sink (Spark files, Delta), the guarantee is exactly-once. Each query needs its own checkpoint.

Triggers

Trigger Behavior Use
(default) New micro-batch when the previous one ends Lowest latency
processingTime="1 minute" One micro-batch per interval Control cost and file size
availableNow=True Processes everything available and stops Scheduled incremental ingestion
continuous="1 second" Continuous, no micro-batch (experimental) Millisecond latency, simple operations

Other operations

Operation Support Note
select, filter, withColumn Yes Same as batch
Stream + static join Yes Enrich with dimensions
Stream + stream join Yes Watermark on both sides and a time condition
dropDuplicatesWithinWatermark Yes (3.5+) Deduplication with bounded state
orderBy Only after aggregation in complete Sorting an infinite stream makes no sense
show(), collect() No Use a sink (memory, foreachBatch)
