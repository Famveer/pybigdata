1. Origem: por que Hadoop, por que Spark

O problema: uma máquina não basta

O Pandas precisa que os dados caibam na memória de uma máquina. Nos anos 2000, indexar a web ia muito além disso.

Escalar vertical Escalar horizontal
Ideia Um servidor maior Mais máquinas comuns
Limite Físico, e o preço dispara Sem limite prático
Custo Hardware Coordenação: rede, falhas, dividir o trabalho

Escalar horizontalmente é a única forma de superar esse limite, mas escrever um programa que sobreviva a falhas de máquinas é muito difícil.

O gargalo era o disco

Velocidade sequencial aproximada, e tempo para ler 1 TB:

Dispositivo Velocidade (ordem de grandeza) Ler 1 TB
RAM 10 GB/s 100 s
SSD NVMe 2,5 GB/s 400 s
Rede de 10 Gb/s 1,25 GB/s 800 s
Disco rígido 200 MB/s 5.000 s ≈ 83 min

A capacidade dos discos cresceu muito mais rápido que sua velocidade, então ler um disco inteiro ficava cada vez mais lento. Agora divida esse mesmo terabyte em 100 discos lidos em paralelo:

\[\frac{1\ \text{TB}}{100 \times 200\ \text{MB/s}} = 50\ \text{s}\]

Este é o argumento central de escalar horizontalmente: discos em paralelo, não discos mais rápidos. A tabela dá outra lição: uma rede de 10 Gb/s é mais rápida que um disco mas mais lenta que a RAM, então mover dados é caro, e daí vem “mover o código até os dados”.

Por que Hadoop?

2003–04: o Google publica os artigos do GFS e do MapReduce. 2006: Doug Cutting e Mike Cafarella criam o Hadoop, uma implementação open source.

Ideia O que resolveu
Máquinas comuns, falhas são normais Os dados são replicados e o trabalho que falhou é refeito sozinho
Mover o código até os dados Evita enviar terabytes pela rede
Só map e reduce O framework cuida da distribuição, não você

Pela primeira vez, qualquer empresa podia processar dados nessa escala.

Por que Spark?

O MapReduce escreve em disco a cada passo, então o trabalho iterativo ou de muitos passos era lento e difícil de expressar.

Hadoop MapReduce Spark
Entre passos Disco Memória quando possível
Trabalho iterativo (ML) Um job por iteração Os dados ficam em cache
API map e reduce, em Java DataFrames, SQL, streaming, ML
Otimizador Nenhum Catalyst + AQE

2009: Matei Zaharia inicia o Spark na UC Berkeley. 2014: vira projeto principal da Apache. O Spark não substituiu todo o Hadoop: continua lendo do HDFS e rodando sobre o YARN.

2. Quanto dá escalar?

Medir o escalonamento: speedup e lei de Amdahl

Com \(T_p\) o tempo com \(p\) processadores:

\[S(p) = \frac{T_1}{T_p} \qquad\qquad E(p) = \frac{S(p)}{p}\]

Se uma fração \(s\) do trabalho é serial (Amdahl, 1967):

\[S(p) = \frac{1}{s + \dfrac{1 - s}{p}} \;\leq\; \frac{1}{s}\]

\(s\) \(p = 10\) \(p = 100\) \(p = 1000\) \(p \to \infty\)
1% 9,2 50 91 100
5% 6,9 17 19,6 20
10% 5,3 9,2 9,9 10

Com \(s = 5\%\), a eficiência em \(p = 100\) é de 17%: 83 dessas máquinas são desperdiçadas na prática. No Spark, \(s\) inclui o trabalho do driver, collect(), operações em uma só partição e a maior task de cada stage.

Então por que o big data funciona? Lei de Gustafson

Amdahl fixa o tamanho do problema. Na prática mais máquinas são usadas para mais dados, e a parte serial não costuma crescer na mesma proporção. Medindo \(s\) na execução paralela (Gustafson, 1988):

\[S_{\text{escalonado}}(p) = s + (1 - s)\,p\]

Com \(s = 5\%\), \(p = 100\): \(S_{\text{escalonado}} = 95\), frente a 17 na lei de Amdahl. Não se contradizem: respondem a perguntas diferentes.

Pergunta Métrica Lei
Mesmos dados, quanto mais rápido? Escalonamento forte Amdahl
Mais dados, mesmo tempo? Escalonamento fraco Gustafson

A maior parte do uso de big data é escalonamento fraco: o job de ontem deve continuar terminando a tempo com o volume maior de hoje. Ao ler uma afirmação de escalabilidade, pergunte primeiro qual das duas ela mede.

Escalável não é o mesmo que rápido: COST

Um sistema pode escalar muito bem simplesmente porque é lento em um núcleo: o custo extra paralelizável parece um bom speedup.

COST (Configuration that Outperforms a Single Thread): o hardware que uma plataforma precisa antes de superar uma implementação competente de uma só thread (McSherry et al., 2015).

Tempos reportados para 20 iterações de PageRank no mesmo grafo:

Sistema Núcleos Tempo
GraphX 128 419 s
Giraph 128 596 s
Uma só thread (SSD) 1 300 s

Consequência para este curso: não use o speedup de um cluster como única prova de que é a ferramenta certa. O Spark paga um custo fixo em planejamento, JVM e coordenação, e primeiro precisa recuperá-lo. Em uma máquina, com dados que cabem na RAM, o Pandas pode empatar ou ganhar (veja o Lab 4). A Aula 12 retoma esta pergunta com números.

3. Arquitetura: onde o código roda

Três tipos de processos

   DRIVER (seu programa)          CLUSTER MANAGER         EXECUTORS (nos workers)
   ┌───────────────────┐  pede    ┌──────────────┐ inicia ┌─────────────────────┐
   │ Python ─py4j─▶ JVM│ ───────▶ │ YARN, K8s ou │ ─────▶ │ JVM: tasks + cache  │
   │ planeja, agenda   │          │ standalone   │        │ Python: só UDFs     │
   └───────────────────┘          └──────────────┘        └─────────────────────┘
             └───────────── envia tasks, recebe resultados ───────▲
Processo Função Se falhar
Driver Roda seu main, constrói os planos, agenda tasks A aplicação morre
Executor Roda tasks e guarda dados em cache Suas tasks são repetidas em outro
Cluster manager Aloca recursos Depende do gerenciador

O PySpark não executa seu código de DataFrames em Python. df.filter(...) só constrói um plano por py4j: os dados são processados na JVM. Por isso o PySpark nativo rende como Scala, e por isso uma UDF Python é tão diferente: só então os dados saem da JVM. No modo local[*], tudo vive em uma máquina, em uma JVM, com threads como espaços de executor.

Exercício: o que isto imprime?

counter = 0
def add(row):
    global counter
    counter += row.value

df.foreach(add)
print(counter)

0 em um cluster, e a documentação chama esse comportamento de indefinido. Antes de executar, o Spark serializa o closure da função e envia uma cópia a cada executor. Cada um atualiza sua cópia, e o counter do driver nunca é tocado. Em modo local pode parecer que funciona em algumas APIs, e por isso esse erro sobrevive aos testes.

O mesmo modelo explica outras surpresas comuns:

Código Roda em Consequência
print(x) dentro de uma UDF Executor Vai para o log do executor, não para seu notebook
df.collect() Tasks, depois driver Todos os dados em uma máquina (spark.driver.maxResultSize, 1 GB)
Uma conexão a BD em um closure Falha ao serializar Abra dentro de foreachPartition

Para contar entre executors, use uma agregação (df.agg) ou um acumulador.

4. O modelo de DataFrame

Mesmo nome, outro objeto

Propriedade Pandas Spark
O que é Valores em memória Um plano: descrição de um cálculo
Mutável Sim (df["x"] = ...) Não: cada operação retorna um novo
Índice Sempre Nenhum
Ordem das linhas Garantida Nenhuma, a menos que ordene
Valores faltantes NaN, None, NaT NULL, e NaN é um valor à parte
df["a"] + 1 Uma Series com resultados Uma Column: uma expressão, sem dados
Execução Imediata Na primeira ação

Por que são necessárias:

  • Imutável + plano: dados perdidos podem ser recalculados pela linhagem, e o otimizador pode reordenar passos.
  • Sem índice nem ordem: uma ordem global forçaria coordenação em cada operação.

Consequência: sem orderBy, “a primeira linha” não significa nada.

As colunas são expressões

F.col("price") * F.col("quantity") não calcula nada. Constrói uma árvore, e isso permite ao Catalyst inspecioná-la e reescrevê-la:

total = F.col("price") * F.col("quantity")     # Multiply(price, quantity)
tier  = F.when(total > 500, "high").otherwise("low")   # CaseWhen(...)

df.withColumn("total", total).withColumn("tier", tier) # no data read yet

Esta é a raiz da diferença com uma UDF: uma árvore de expressões pode ser otimizada, enquanto uma função Python é opaca (Aula 6).

Hábito do Pandas Spark Por quê
Um laço for adicionando colunas select com todas Cada withColumn adiciona um nó ao plano: planos grandes são lentos de analisar
.apply(fn) F.when, F.* Expressões nativas rodam na JVM e são otimizadas
df[df.x > 1] e reutilizar Igual, mas em uma variável Cada ação recalcula todo o plano

5. Schemas e formatos

Inferir um schema tem um custo, e um risco

spark.read.csv(path, header=True, inferSchema=True)  # uma passada extra
spark.read.csv(path, header=True, schema=my_schema)  # sem passada extra
spark.read.parquet(path)                             # schema no arquivo

Custo. Com samplingRatio = 1.0 por padrão, inferir percorre todo o arquivo antes de sua consulta começar: em 1 TB de CSV a 200 MB/s, são 83 min em um disco.

Risco. O schema inferido depende dos dados que havia hoje. Um "N/A" em uma coluna numérica a torna string, e o pipeline de amanhã quebra ou muda de tipo em silêncio.

No Spark 4, o modo ANSI vem ativo por padrão (spark.sql.ansi.enabled = true), então um cast inválido lança um erro em vez de retornar NULL:

F.col("x").cast("int")       # erro com "abc" (ANSI ativo)
F.col("x").try_cast("int")   # NULL com "abc"

nullable=False em um schema é uma declaração, e não uma restrição aplicada ao ler arquivos.

Linha ou coluna: o formato muda os bytes lidos

 CSV / JSON (linhas)                  Parquet (colunas)
 ┌───┬─────┬───────┬────┐             ┌────┐ ┌─────┐ ┌───────┐ ┌────┐
 │ 1 │ ana │ north │ 10 │             │ 1  │ │ ana │ │ north │ │ 10 │
 │ 2 │ bo  │ south │ 20 │             │ 2  │ │ bo  │ │ south │ │ 20 │
 └───┴─────┴───────┴────┘             └────┘ └─────┘ └───────┘ └────┘
   ler 1 coluna analisa todas           ler 1 coluna só lê essa

Com \(C\) colunas de largura similar e uma consulta que usa \(c\), a fração de bytes lidos é cerca de \(c / C\):

CSV Parquet
Consulta usa 2 de 20 colunas 100% dos bytes Cerca de 10%
Compressão Fraca: valores misturados em uma linha Forte: valores parecidos juntos, por coluna
Filtro price > 100 Lê tudo Pula grupos de linhas com estatísticas min/max
Schema Inferido ou declarado Guardado no arquivo
Legível por humanos Sim Não

Para uma consulta analítica, isso pode valer mais do que adicionar máquinas, como mostra o problema a seguir.

6. Problema integrador

Você precisa de um cluster?

Relatório diário: 6 TB de CSV, 20 colunas de largura similar, a consulta usa 2. Deve ler tudo em menos de 1 hora. Cada nó tem um disco de 200 MB/s.

  1. Quantos nós só para a leitura, com CSV?
  2. Se 5% do job é serial, quantos desses nós se ganham na prática?
  3. E se os dados estivessem em Parquet?
  1. \(\dfrac{6\ \text{TB}}{200\ \text{MB/s} \times 3.600\ \text{s}} = 8{,}3\), então 9 nós, e inferSchema dobraria a leitura.
  2. Amdahl: \(S(9) = 1 / (0{,}05 + 0{,}95/9) \approx\) 6,4: 9 nós rendem como 6,4, então são necessários ainda mais.
  3. Cerca de 10% dos bytes: \(600\ \text{GB} / 200\ \text{MB/s} =\) 3.000 s = 50 min, em um nó.

Conclusão: o formato economizou mais de oito máquinas. É uma estimativa que ignora a compressão (que ajuda ainda mais o Parquet), a CPU e tudo depois da leitura. Mas mostra a ordem de pensar: primeiro reduza o trabalho, depois paralelize o que resta. Escalar um plano desperdiçador só torna o desperdício mais rápido.
