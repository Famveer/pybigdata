1. O modelo de dados do Python

Variáveis são nomes, não caixas

Uma variável guarda uma referência a um objeto. Atribuir copia a referência, não o objeto.

Tipo Propriedades Busca por valor Uso típico
list Ordenada, mutável \(O(n)\) Sequências
tuple Ordenada, imutável \(O(n)\) Registros fixos, chaves de dict
dict Chave-valor, mutável \(O(1)\) em média Buscas, agrupar
set Sem duplicatas \(O(1)\) em média Pertinência, deduplicar

Exercício: o que cada linha imprime?

a = [1, 2, 3];   b = a;   b.append(4);   print(a)
c = a.copy();    c.append(5);            print(a)

def add(x, acc=[]):
    acc.append(x)
    return acc
print(add(1), add(2))

[1, 2, 3, 4], porque a e b são a mesma lista. Depois [1, 2, 3, 4], porque c é uma cópia. Depois [1, 2] [1, 2]: um valor padrão é criado uma vez, ao definir a função, e é compartilhado por todas as chamadas.

Funções são valores, e comprehensions são expressões

discount = lambda price, pct: price * (1 - pct)      # um objeto função
squares  = [n ** 2 for n in numbers]                 # list comprehension
prices   = {item: p * 1.23 for item, p in rows}      # dict comprehension

Por que importa além da sintaxe. Toda a API do Spark recebe funções e expressões como dados:

Ideia do Python Onde reaparece
Uma função é um valor .apply(fn), UDFs
Um closure captura variáveis O Spark serializa uma função com o que capturou, e envia uma cópia a cada executor (Aula 3)
Uma comprehension sobre um iterável yield e iteradores são como o Spark encadeia transformações narrow sem listas intermediárias (Aula 5)

Geradores mantêm a memória constante:

sum([x * 2 for x in rows])   # primeiro toda uma lista: O(n)
sum(x * 2 for x in rows)     # um valor por vez: O(1)

A mesma soma, com um uso de memória muito diferente. É a ideia do pipelining, em uma linha de Python.

2. Por que Pandas

Por que Pandas?

O Python não tinha uma boa forma de trabalhar com dados tabulares:

Alternativa Limitação
Excel Cerca de 1 milhão de linhas, trabalho manual, difícil de reproduzir
Listas e dicts do Python Loops longos, lentos com muito volume
NumPy Rápido, mas um só tipo por array, sem rótulos nem nulos
R Tinha data.frame, mas fora do ecossistema Python

2008: Wes McKinney, então no fundo AQR Capital, começa o Pandas para analisar dados financeiros. Vira open source em 2009, sobre o NumPy.

O mesmo total, com menos código

# Python puro
totais = {}
for row in rows:
    totais[row["cat"]] = totais.get(row["cat"], 0) + row["price"]

# Pandas
df.groupby("cat")["price"].sum()

3. Por que vetorizar é mais rápido

Um milhão de inteiros, duas disposições

 Lista Python:  [ptr][ptr][ptr][ptr] ...     cada ponteiro ─▶ um objeto int à parte
                  │    │    │                 espalhados pela memória
                  ▼    ▼    ▼
                [28 B][28 B][28 B]

 Array NumPy:   [ 8 B | 8 B | 8 B | 8 B | ... ]    os valores crus, contíguos, um tipo
Lista Python NumPy int64
Por valor Ponteiro de 8 B + objeto de 28 B = 36 B 8 B
1 milhão de valores 36 MB 8 MB
Por soma Verifica tipos, segue ponteiros, cria um resultado Uma instrução de máquina

Confira: sys.getsizeof(1) retorna 28, em CPython de 64 bits.

Por que o laço é lento: Python não sabe que a lista tem inteiros, então cada iteração verifica o tipo, desempacota, soma e cria um objeto. arr * 2 verifica uma vez e roda um laço compilado sobre memória contígua. Costuma ser dezenas de vezes mais rápido: meça com %timeit.

Exercício: ordene por velocidade

Todas adicionam 15% de imposto a uma coluna de 10 milhões de números.

df["t"] = [row.price * 1.15 for row in df.itertuples()]        # A
df["t"] = df.apply(lambda row: row["price"] * 1.15, axis=1)    # B
df["t"] = df["price"].apply(lambda p: p * 1.15)                # C
df["t"] = df["price"] * 1.15                                   # D

O habitual, do mais rápido ao mais lento: D ≫ C, A ≫ B. Meça com %timeit.

Python por linha? Por quê
D Não Um laço compilado sobre a coluna
C Uma chamada por valor Empacota cada número em um objeto Python
A Uma namedtuple por linha Constrói um objeto Python para cada linha
B Uma Series inteira por linha A pior: cria um objeto com índice, para cada linha

A regra é ver se Python roda por linha. axis=1 quase sempre é sinal de algo que pode ser reescrito.

É o mesmo custo de uma UDF Python no Spark (Aula 6).

4. O DataFrame: colunas e tipos

Um DataFrame são colunas tipadas mais um índice

Cada coluna tem um dtype, então a memória é previsível: linhas × bytes por valor.

dtype Bytes por valor Para 1 milhão de linhas Nota
int64, float64 8 8 MB Padrão para números
int32, float32 4 4 MB Basta para muitas colunas
int8 1 1 MB De −128 a 127
object (strings) 8 + ~58 ~66 MB Ponteiros a objetos Python
category, 5 valores 1 + uma tabela pequena ~1 MB Codificação por dicionário

object é uma lista disfarçada: o array guarda ponteiros, e os laços compilados rápidos se perdem. category guarda cada valor distinto uma vez, mais um inteiro por linha. É a mesma ideia da codificação por dicionário do Parquet (Aula 8).

NaN pode mudar seu tipo

pd.Series([1, 2, 3]).dtype          # int64
pd.Series([1, 2, None]).dtype       # float64: NaN é float
pd.Series([1, 2, None], dtype="Int64")   # com nulos: <NA>, mantém o tipo

IDs grandes perdem precisão além de \(2^{53}\) ao serem forçados a float64. Assim, um só valor faltante pode corromper em silêncio uma coluna de IDs.

Por isso uma coluna de IDs deve ser lida com um tipo explícito: dtype={"id": "Int64"}, em vez de deixar para a inferência.

Visão ou cópia? O erro clássico

df[df["price"] > 100]["discount"] = 0.1      # atribuição encadeada
print(df["discount"])                        # pode não ter mudado!

df.loc[df["price"] > 100, "discount"] = 0.1  # correto: uma só operação

A primeira linha tem dois passos: df[mask] dá um objeto novo, e a atribuição modifica esse objeto, não df. Se o original mudava dependia de detalhes internos que decidem entre visão e cópia. Daí SettingWithCopyWarning, e esse aviso é um erro que não se deve ignorar.

Versão do Pandas Comportamento
2.x, por padrão Ambíguo: avisa, e pode modificar ou não
2.x com copy_on_write = True, ou 3.0 (padrão) Um objeto derivado se comporta como cópia: a atribuição encadeada nunca modifica o original

Copy-on-Write remove a ambiguidade, e também economiza memória: só se copia de verdade ao gravar. Este curso usa Pandas 2.x, então escreva da forma que serve em ambos: um só .loc.

O Spark evita todo o problema por projeto: DataFrames são imutáveis, e withColumn sempre retorna um novo.

5. Operações e seu custo

Split, apply, combine, e quanto custa cada um

groupby é split-apply-combine (Wickham, 2011): dividir linhas por chave, aplicar uma função a cada grupo, e combinar os resultados.

Operação Algoritmo Tempo Pico de memória Exposta a
Filtro, aritmética Laço compilado \(O(n)\) Resultado de \(O(n)\)
sort_values Ordenação por comparação \(O(n \log n)\) \(O(n)\)
groupby().sum() Tabela hash por chave \(O(n)\) \(O(\text{grupos})\) Python, se houver .apply
merge Hash do lado menor \(O(n + m + \text{saída})\) \(O(\text{saída})\) Duplicatas: \(\sum_k a_k b_k\)
groupby().apply(fn) Python por grupo \(O(n)\) com constante alta Lento por grupos

A surpresa clássica no merge: uma chave não única em ambos os lados multiplica linhas, e o resultado pode ser muito maior que a entrada (Aula 4). validate="many_to_one" faz falhar com clareza, em vez de em silêncio:

orders.merge(customers, on="customer_id", validate="many_to_one")

Quase todas essas operações usam um núcleo. Os laços compilados do Pandas são de uma thread na maioria das operações. Assim, pela lei de Amdahl com \(s \approx 1\), seus 16 núcleos aqui não acrescentam nada. Esse é o vazio que outras ferramentas preenchem.

6. Problema integrador

Cabe no meu laptop?

Um laptop de 16 GB, e 50 milhões de linhas: 3 int64, 2 float64, e region, uma coluna de texto com 5 valores. Você precisa de um merge com um resultado de tamanho similar.

  1. Memória com os tipos padrão? 2. O merge cabe? 3. E com tipos melhores? 4. O que mais pode ser feito?
  1. Números: \(5 \times 8 =\) 40 B. Texto: 8 + 58 = 66 B. Total 106 B/linha, então \(50\text{M} \times 106 =\) 5,3 GB.
  2. Arriscado. Durante o merge, entrada e saída vivem ao mesmo tempo: cerca de 10,6 GB, sem contar o sistema operacional e o que mais estiver aberto. É a regra de 5 a 10 vezes o tamanho do arquivo em ação.
  3. category (1 B) + int32/float32 (4 B cada, se as faixas permitirem): \(5 \times 4 + 1 =\) 21 B/linha, ou 1,05 GB. 5× menos, com os mesmos dados, e o merge cabe com folga.
  4. Leia menos. pd.read_parquet(path, columns=[...]) e filtre na origem. Se ainda for demais, processe por pedaços, ou mude de ferramenta (Aula 12).

O método importa mais que os números: largura do tipo × linhas dá a resposta antes que a máquina congele.
