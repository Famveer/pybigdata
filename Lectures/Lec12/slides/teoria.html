1. What the measurements say

Same query, same machine

Lab 12, on 24 cores: revenue by segment and category, with a filter and two joins. Best time per tool, on Parquet:

Rows Pandas Polars DuckDB Spark
1 M 0.11 s 0.02 s 0.03 s 0.33 s
5 M 0.46 s 0.04 s 0.04 s 0.34 s
20 M 2.14 s 0.11 s 0.08 s 0.49 s

Fit the simplest model: a fixed cost \(a\) plus a cost per row \(b\), using the extremes:

\[T(n) = a + b \cdot n\]

Tool Fixed cost \(a\) Cost per row \(b\)
Pandas ≈ 0 107 ns
Spark 0.32 s 8.4 ns
Polars 15 ms 4.7 ns
DuckDB 27 ms 2.6 ns

Four rows of a table have just explained the entire debate: Spark has a huge \(a\), and Pandas a huge \(b\).

Where the lines cross

Two tools tie when \(a_1 + b_1 n = a_2 + b_2 n\):

\[n^* = \frac{a_2 - a_1}{b_1 - b_2}\]

Comparison \(n^*\) Reading
Spark vs Pandas \(\dfrac{0.32}{(107 - 8.4) \times 10^{-9}} \approx\) 3.2 M rows Below it Pandas wins, above it Spark does
Spark vs Polars Never Spark has more \(a\) and more \(b\)

The model predicted reality. It places the crossover between 1 M and 5 M, and that is exactly what the table shows: Pandas wins at 1 M (0.11 vs 0.33 s), and loses at 5 M (0.46 vs 0.34 s).

The honest limits of this analysis:

  • It is one machine, with warm cache, and “best of 2” runs: not a benchmark.
  • \(T(n)\) fitted on two points, so linearity is an assumption.
  • It ignores memory: Pandas may break long before it gets slow.

The central conclusion stands up to those limits. On one machine, Spark’s \(b\) is not better than Polars’ or DuckDB’s. Its advantage must come from what they cannot do: use more machines. Spark is not for speed on one machine.

2. Why they are fast: the hardware

107 ns vs 2.6 ns: where do 40× come from?

All of them run a hash join here. The gap comes from how they use the hardware, in four independent levers:

Lever Pandas Polars, DuckDB Rough gain
Cores 1, in most operations All Up to 24× here, by Amdahl
Vectorized execution Partly (NumPy, per column) Batches, at all stages Tens of times
Plan optimization None: eager Pushdown, pruning, join order Depends on the query
Materialization Each step creates a full result Streaming between operators Memory, and cache misses

Approximate latencies (order of magnitude):

Operation Time Relative to one core cycle
CPU cycle 0.3 ns 1
Main memory 100 ns 300

A memory miss costs hundreds of operations. A modern engine is, above all, a design for not missing the cache.

From row-at-a-time to vectors

Volcano, the classic model: each operator asks its child for one row at a time. Clean, composable, and terribly slow: a virtual call per operator and per row, and the CPU’s branch predictor and cache can’t help.

for row in child:                  # Volcano: interpret per row
    if row.price > 100: yield row

selected = price[price > 100]      # Vectorized: tight loop per batch

Vectorized execution (Boncz et al., 2005) keeps the same operator tree, but passes batches of about a thousand values of one column. The result:

Effect Why
Interpretation paid once per batch Dispatching cost is split across many values
Cache A column is contiguous, so the prefetcher works, and the batch fits in the cache
SIMD One instruction processes several values, which only works over contiguous data

The paper reports one to two orders of magnitude. Part of the 40× we saw comes from here, and part from using 24 cores.

Spark uses a different solution to the same problem: whole-stage codegen, which compiles the plan down to one loop (Lecture 5). Both beat Volcano. What Spark pays beyond this is the JVM and coordination, which make up its \(a\).

3. Memory and out-of-core

Time is only half the story

Lab 12: query on 5 million rows, orders.parquet is 63 MB on disk. Peak memory of a separate process, minus the 139 MB of the empty one:

Tool Peak (net) Bytes per row × file size
Pandas 734 MB 147 11.7×
Polars 178 MB 36 2.8×
DuckDB 83 MB 17 1.3×

Why Pandas needs so much: it decompresses whole columns, each merge creates a full copy, and strings are Python objects. This explains the old rule of thumb: plan on 5 to 10 times the dataset’s size in RAM.

On a 64 GB machine, by this measure, Pandas stops at around 435 million rows, or about 5.5 GB of Parquet.

The limit that matters: Polars and DuckDB, when memory runs out, can use disk (out-of-core): hash tables and sorts are partitioned and spill, like Spark’s shuffle does. Lab 12 ran 5 million groups with a 300 MB limit in DuckDB. Pandas has no such path: it simply dies.

Thus, for one machine, “does it fit in RAM?” is the wrong question. Better: does it fit on its disk?

4. Apache Arrow

A common format makes conversion free

Before Arrow, each pair of tools needed its own conversion: \(n(n-1)\) converters, each copying and serializing. Arrow defines a standard in-memory columnar layout, so \(n\) tools speak one format, and sharing a buffer needs no copy (the format is relocatable, and has no pointers to rewrite).

Lab 12, 1 million rows:

Conversion Time What happens
Pandas → DuckDB 0.002 s Reads the same buffers
Arrow → Polars 0.003 s Zero copy
Arrow → Pandas 0.017 s Some columns must be converted
Spark → Pandas 0.89 s Crosses JVM to Python
Pandas → Spark 1.70 s Crosses, in the other direction

A difference of three orders of magnitude between “same memory” and “crossing the JVM”.

The JVM’s own Arrow option helps a lot, yet it is off by default in PySpark 4.0. Measured, 300,000 rows:

arrow.pyspark.enabled Pandas → Spark Spark → Pandas
false (default) 5.09 s 1.35 s
true 0.52 s (10×) 0.31 s (4×)

5. Pandas API on Spark

Same syntax, different semantics to maintain

pyspark.pandas keeps pd’s API. Its use case is migrating existing code, not speed: the table shows 0.53 s, behind Spark’s 0.48 s. Yet Pandas promises things that are expensive on a cluster:

Pandas promises On Spark it needs Cost
A row index Generating one One of three strategies, below
Stable row order An ordering, if at all A sort, or no guarantee
Immediate errors Lazy evaluation Errors appear later
Division by zero gives inf ANSI mode off It refuses to start otherwise

The index: the cost of a promise

compute.default_index_type How Cost
sequence (default) 0, 1, 2… through a single partition Bottleneck: back to Amdahl with \(s \to 1\)
distributed-sequence 0, 1, 2… computed per partition One extra job
distributed Increasing, not consecutive Low

Check what the code really requires. If the logic never uses consecutive indices, distributed removes a cost that the program did not need, and this is the general lesson of the block: semantics you do not need are costs you can avoid.

6. How to decide

A criterion in four questions

Ask in this order, and stop at the first decisive answer:

# Question If yes
1 Do I need streaming, Delta transactions, or a multi-tenant cluster? Spark: not a matter of speed, but of features
2 Does it exceed the disk of the largest affordable machine? Spark, as nothing else scales out
3 Does a failure need recovery from mid-job? Long jobs? Spark: others restart from zero
4 Otherwise, one machine: team and code? SQL: DuckDB. Python: Polars. Small, interactive: Pandas

Do not overdo the argument in the other direction:

  • “Fits on one machine” depends on the machine. A large cloud VM, with hundreds of GB, processes a lot, and sometimes costs less than a cluster.
  • Fault tolerance is a feature. A 6-hour DuckDB job restarts from zero on a failure. A Spark job retries one task.
  • They combine, thanks to Arrow: Spark for the heavy ETL, DuckDB to explore its output, Polars for features.

When not to use Spark? When you would pay its \(a\), and use none of what it buys.

7. Integrating problem

Which tool, and why?

Use the criterion, and the numbers from this lecture. Justify in one sentence.

  1. A 300 MB CSV by email, and three charts by this afternoon.
  2. Every day, 2 TB of logs on S3, joined with Delta tables, writing Silver.
  3. A BI team queries 15 GB of Parquet in SQL, from a notebook, with no cluster.
  4. A Pandas forecast worked on 1 year; now it needs 10 years, 80 GB.
  5. An API must answer aggregations over a 500 MB file in under 100 ms.
  1. Pandas. \(n\) is far below the crossover, and \(a \approx 0\): setting up anything else does not pay off.
  2. Spark. Questions 1 and 2 answer it: Delta and distributed sources.
  3. DuckDB. SQL with no server; 15 GB is small, and it can spill.
  4. Pandas API on Spark to move quickly with little rewriting, or Polars on a large machine: at 11.7× the file, Pandas needs far too much RAM. In the medium term, rewrite.
  5. DuckDB or Polars, in the service’s process. Spark’s \(a\) alone, of 320 ms, exceeds the 100 ms budget, whatever the data’s size: this is decided by the fixed cost, with no need to measure.
