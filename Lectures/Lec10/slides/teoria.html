1. The model: unbounded table and two times

A stream is a table that only grows

The input is an unbounded table to which rows are appended. You write a query as if it ran over the whole table, and the engine computes it incrementally (Armbrust et al., 2018).

Prefix consistency: the result at any moment equals the result of the same query, run in batch, over some prefix of the input. This is the model’s central promise, and it is why a stream’s logic can be reasoned about like a batch’s.

Output mode What each trigger writes Requires
append Only rows that will never change With aggregation: a watermark
update Rows that changed
complete The whole result, again State is never cleaned

Why append needs a watermark in an aggregation: a count for 10:00 can still change, so writing it would be a promise that cannot be kept. It can only be written once the engine decides that the window will not change. So some latency is the price of immutable output.

Why this cannot be escaped. On an unbounded, out-of-order stream, you cannot know whether a window is complete. Dataflow frames it as a forced compromise between three goals: correctness, latency and cost (Akidau et al., 2015). Each of this lecture’s parameters picks a point in that trade-off.

2. Micro-batches and capacity

Can the pipeline keep up?

With arrival rate \(\lambda\) (rows/s), and capacity \(\mu\) (rows/s the job can process), let \(\rho = \lambda / \mu\).

Behavior
\(\rho < 1\) Stable: each micro-batch drains what arrived
\(\rho > 1\) Unstable: the backlog grows without limit, as \((\lambda - \mu)\,t\)

Latency has a floor: an event waits for its batch to start, and then for it to finish. At a batch duration \(B\), the latency reaches around \(2B\) at worst. Batches get longer with more data, so as \(\rho \to 1\) latency grows quickly.

After an outage of duration \(T\), the backlog is \(\lambda T\), and it drains at \(\mu - \lambda\):

\[T_{\text{catch-up}} = \frac{\lambda T}{\mu - \lambda} = T \cdot \frac{\rho}{1 - \rho}\]

\(\rho\) (normal load) Catch-up after a 1 h outage
50% 1 h
80% 4 h
95% 19 h

The real sizing criterion is not “does it keep up today?” but “how long does it take to recover?”

Triggers: latency against cost

Trigger Batch starts Latency Cost
Default When the last one ends Lowest for micro-batch Cluster always on
processingTime="1 minute" Every interval Up to about 2 min Larger batches, larger files
availableNow=True Once: drains, and stops That of the schedule Only pay while it runs
continuous="1 second" No batches (experimental) Milliseconds Few operations, at-least-once

availableNow is the often-overlooked option. Do you really need results within seconds? If every hour is enough, this runs an hourly job with the same streaming code and checkpoint: it processes only what is new and then releases the cluster.

Small triggers mean small files: a file sink with a 10 s trigger writes at least 8,640 commits per day, and at least that many files, which then require compaction (Lectures 8 and 9).

3. Windows and state

How much memory does a window cost?

A window of length \(L\) sliding every \(S\): each event belongs to \(\lceil L / S \rceil\) windows, so the work per event multiplies by that factor.

State. An aggregation keeps, per window and key, its partial state (Lecture 4’s distributive or algebraic state). A window remains open while it may receive data: its length plus the watermark’s delay \(\tau\). With \(K\) active keys and \(b\) bytes per entry:

\[\text{state} \approx \frac{L + \tau}{S} \times K \times b\]

Query, \(K = 100{,}000\), \(b = 200\) B, \(\tau = 10\) min Open windows State
Tumbling, 5 min 3 60 MB
Sliding, 10 min every 1 min 20 400 MB
Sliding, 1 h every 1 min 70 1.4 GB
complete, or no watermark Grows forever Until it fails

State belongs to the executors, in memory with the default store, where it causes GC pauses as it grows. RocksDB moves it to native memory and local disk. It is backed up in the checkpoint, so it adds to the batch’s duration.

4. Watermarks

The formal rule, and its guarantee

\[W = \max(\text{event time seen}) - \tau\]

A window ending at \(T\) is kept until \(W > T\). Then it is emitted (in append) and its state is released.

Detail Consequence
\(W\) only moves forward A late event never moves it back
Recomputed at the end of each batch Applies from the next batch on
Decided by windows, not by events A late event gets in if its window is still open
With several inputs: the minimum \(W\) The slowest stream holds back all the results

The guarantee goes in one direction only (Spark documentation):

  • Data delayed less than \(\tau\): never dropped.
  • Data delayed more than \(\tau\): may or may not be aggregated.

So \(\tau\) is a lower bound on tolerance, and not an exact cutoff. Do not rely on late data being dropped: results may differ between runs, according to how the batches fell.

Choosing \(\tau\) is choosing among three costs

Increasing \(\tau\) Effect
Correctness Fewer dropped events
Latency Results appear later: at least \(\tau\) past the window’s end, in append
Cost More open windows, hence more state: \((L + \tau)/S\)

So \(\tau\) should come from data, rather than habit. Measure the delay distribution \(D = t_{\text{processing}} - t_{\text{event}}\):

Delay percentile Example If \(\tau\) = this value
p50 2 s Half of the events are in danger
p99 3 min About 1% at risk
p99.9 2 h Almost none at risk, but results 2 h late

The tail is usually long, as a phone with no signal can take hours, and following it costs in proportion. Usually \(\tau\) covers the p99, and what arrives later is handled apart: a daily batch correction, with MERGE, on the Bronze layer’s data.

This is the lambda-like pattern with one codebase: streaming gives speed, and reprocessing gives completeness.

5. Exactly-once, precisely

What exactly-once really requires

An event may be processed several times. What is guaranteed is that its effect on the output applies once, which needs:

Component Requirement Example
Source Replayable, with offsets Kafka, files. A socket does not qualify
Engine Records what each batch reads, and is deterministic Checkpoint
Sink Idempotent or transactional File sink, Delta 
 1. write offsets/N    ← "batch N will read this range"     (before processing)
 2. process, write to the sink
 3. write commits/N    ← "batch N is finished"              (after the sink)

Exercise: the process dies. What happens on restart?

Crash On restart Why it is safe
Between 1 and 2 Re-runs N with the same range Deterministic
During 2 Re-runs N: rewrites to the sink The sink must be idempotent
Between 2 and 3 Re-runs a finished batch Here is the catch: same reason

The sink is where the guarantee is won or lost. The file sink writes a manifest per batch, and Delta a transaction with the (appId, version) pair, so that a repeated batch is ignored.

Not every sink offers it

Sink Guarantee Why
File Exactly-once Readers use the manifest: uncommitted files are invisible
Delta Exactly-once Transaction with (appId, version)
Kafka At-least-once Cannot retract what was published. A retry duplicates
foreach At-least-once Your code runs on each row
foreachBatch Depends on you Use batchId to deduplicate

The most common mistake, in foreachBatch:

def write(df, batch_id):
    df.write.mode("append").jdbc(url, table)           # duplicates
def write(df, batch_id):
    merge_target(df, on="event_id")                    # idempotent

Exactly-once ends at the sink. A side effect, such as sending an email per row, is your responsibility.

6. Integrating problem

Size this stream

10,000 events/s from Kafka. Revenue per product in sliding windows of 10 min every 1 min. 50,000 active products, 200 B per state entry. A sample shows a p99 delay of 2 min. The job handles 12,500 events/s at most. It writes to Delta.

  1. \(\tau\)? 2. Size of the state? 3. Is it stable? 4. Catch-up after a 2 h outage? 5. End-to-end guarantee?
  1. 2 min covers the p99. A daily batch job can reconcile the rest.
  2. \((10 + 2) / 1 =\) 12 open windows \(\times\) 50,000 \(\times\) 200 B \(=\) 120 MB. Manageable. A window every second would multiply this by 60.
  3. \(\rho = 10{,}000 / 12{,}500 =\) 80%: stable, with a thin margin.
  4. \(2\ \text{h} \times 0.8 / 0.2 =\) 8 hours at reduced freshness. If unacceptable, double the capacity: \(\rho = 40\%\) gives 80 min.
  5. Exactly-once: Kafka is replayable, the checkpoint records the offsets, and Delta is transactional. If Kafka’s retention is shorter than the outage, data is lost: the guarantee assumed a replayable source, so size that retention beyond your longest plausible outage.
